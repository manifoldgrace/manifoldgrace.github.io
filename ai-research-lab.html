SDLC · SOFTWARE DEVELOPMENT LIFE CYCLE

Lifecycle considerations before you build

Use the lifecycle to connect purpose, requirements, design, implementation, testing and ongoing responsibility. These stages repeat as evidence changes; security, ethics, accessibility and QA run throughout.

1. Discovery & feasibility

Define the problem, users, intended benefit, constraints and alternatives. Decide whether AI is warranted and what would justify stopping.

Evidence: Problem statement, scope, stakeholder map and feasibility decision.

Project considerations →

2. Requirements & acceptance

Specify functional behaviour, data needs, privacy, accessibility, performance and error limits. Agree measurable acceptance criteria and prohibited uses before building.

Evidence: Versioned requirements and traceable acceptance tests.

Acceptance review →

3. Architecture & design

Map data flow, interfaces, trust boundaries, permissions and failure modes. Choose appropriate components and plan safe fallback, monitoring and rollback.

Evidence: Architecture diagram, threat model, data contracts and design review.

Architecture discussions →

4. Implementation & integration

Build small increments, version changes and review dependencies. Keep data handling, computation and rendering separate; verify component interactions.

Evidence: Reviewed source, reproducible configuration and integration evidence.

5. Verification & validation

Check implementation against requirements and suitability for the intended use. Test normal, edge, invalid and failure cases; investigate subgroup impacts and document limitations.

Make an evidence-based release decision. Validate the deployment environment, access controls, recovery and support arrangements; begin with a bounded pilot.

ENGINEERING & ETHICS · BREAK, FIX & VERIFY

Test the system, challenge the claim

Use synthetic fixtures to test the same algorithms as the ten experiments. Introduce a controlled fault in the test harness, observe the failures, then remove it and rerun. Live project algorithms remain unchanged by fault selection.

  1. Define requirement
  2. Predict failure
  3. Run baseline
  4. Inject fault
  5. Inspect evidence
  6. Apply fix
  7. Run regression
  8. Review residual risk

Ready: 20 checks across ten projects. No external systems are targeted.

How to break it ethically

Use the supplied synthetic cases, your own non-sensitive examples and authorised local tests. Challenge empty inputs, duplicates, thresholds, irrelevant retrieval, ambiguous categories and constant series. Define an expected result before running. Keep scope local: these exercises do not scan or attack other websites.

Controlled local faults, synthetic data and explicit expected outcomes.

How to fix and verify

Reproduce the failing case, identify its cause, change one control, then rerun the failure case and the full regression suite. The Apply fix button removes the simulated harness fault; it does not patch production code. A real fix requires a reviewed source change, regression evidence and a deployment/rollback plan.

Reproduce → isolate → correct → regress → document remaining limits.

Architecture & cybersecurity

Separate input handling, validated computation and safe output rendering. In production, add authenticated identities, server-side authorisation, isolated workloads, bounded resources, secret management, dependency review, safe logs and monitoring. Browser-only fixtures verify algorithm behaviour; they cannot verify backend isolation or access controls that are not present.

Define trust boundaries and verify controls where they actually run.

Ethics & evidence

Define affected people, intended use, harms and review routes. Test subgroup outcomes and abstention where applicable, examine evidence quality and document uncertainty. A passing selection-rate test proves arithmetic on a fixture, not social fairness. Twenty passing cases provide bounded regression evidence, not assurance for unseen data.

Separate observed behaviour from broader claims about fairness and safety.

Standards & review gates

Use NIST AI RMF to structure Govern, Map, Measure and Manage activities. Use OWASP ASVS to select and verify relevant application-security requirements. Record the version, requirement, applicability, evidence, owner and unresolved gaps. These learning exercises are not certification or a completed standards assessment.

Map controls to requirements and collect evidence; do not assume compliance.

Next model-backed extension

No trained model or persistent service is connected here yet.

Evaluation dataset → model comparison → private records → operational review.

NEXT STEPS · FROM DEMONSTRATION TO ASSURANCE

Build stronger evidence

Progress through these stages after the break–fix exercises. Each is planned work, with a concrete result to review before moving on.

  1. Expand evaluation cases

    Build a versioned set of normal, edge, invalid and adversarial examples. Record expected outcomes before running, include subgroup cases where relevant, and keep a separate held-out evaluation set.

    Evidence: dataset provenance, permissions, expected results, coverage gaps and repeatable test reports.

  2. Visualise model behaviour

    Add ranking charts, confusion matrices, threshold curves, group comparisons and anomaly plots. Show sample sizes, uncertainty and assumptions so a chart supports interpretation rather than implying certainty.

    Evidence: plots linked to saved run inputs and outputs, with concise explanations of observed trade-offs.

  3. Compare trained models

    Start with one text classifier. Run the transparent baseline and a trained model on the same evaluation cases; record model version, licence, latency, errors, calibration and relevant subgroup performance.

    Evidence: reproducible baseline-versus-model comparison, model documentation and a reasoned decision about when to abstain or request human review.

  4. Secure persistent records

    Add authenticated private storage and project-level permissions. Verify server-side authorisation, tenant separation, secret handling, retention and deletion before using sensitive research data.

    Evidence: trust-boundary diagram, threat model, access-control tests and a reviewed retention policy.

  5. Review deployment readiness

    Review requirements, ethical impacts and applicable security controls; document unresolved risks and obtain independent review. Then test monitoring, incident handling and rollback in a controlled deployment.

    Evidence: requirements-to-test mapping, research report, operational runbook and a justified release or no-release decision.

Start here: expand the evaluation cases. More passing fixtures strengthen coverage; unseen-data performance and production assurance still require separate evidence.

AFTER READINESS · OPERATE, REVIEW & RESEARCH

What comes after?

Once a release is justified, move through controlled operation and continuing review. These are future stages; the current laboratory remains a browser demonstration.

  1. Run controlled pilots

    Begin with a limited, authorised user group and low-consequence tasks. Set measurable success criteria, stop conditions, human review and a fallback before widening use.

    Evidence: pilot protocol, consent where applicable, user feedback and a documented decision to continue, revise or stop.

  2. Monitor changing behaviour

    Track quality, latency, failures, data drift and subgroup outcomes against the approved baseline. Set alert thresholds and owners, minimise logged personal data and review whether the original purpose still holds.

    Evidence: monitoring history, drift investigations, service objectives and documented responses.

  3. Practise incident recovery

    Run authorised tabletop exercises and controlled recovery drills. Test escalation, rollback, restoration and communication; verify that failures can be contained without continuing harmful decisions.

    Evidence: drill results, incident timelines, recovery checks and regression tests for fixes.

  4. Reassess societal impacts

    Review accessibility, exclusion, contestability, privacy and unintended uses with affected people and independent reviewers. Compare realised benefits and harms with the original assumptions, including reasons to restrict or retire the system.

    Evidence: updated impact assessment, stakeholder findings, appeal outcomes and a reasoned continuation or retirement decision.

  5. Reproduce and contribute

    Package methods, permitted data, versions and limitations for independent replication. Compare findings with prior research, share only authorised material and turn unresolved questions into the next hypothesis.

    Evidence: reproducible research package, external review, documented contribution and a new testable research question.

Continuing cycle: observe → investigate → improve → revalidate. Higher stakes or wider deployment require stronger evidence and renewed review.

COMPLETE THE LIFECYCLE · ADAPT TO THE PROJECT

Key considerations through project end

AI projects can combine many methods, domains and deployment settings. Their milestones depend on the intended use, data, architecture and consequences of failure; the families below overlap rather than form a fixed list of 1,000 distinct types.

How project shapes differ

Swipe across project families; expand a card for milestones, architecture, challenges and review gates.

Rules & expert systems

Milestones: Elicit rules → resolve conflicts → validate exceptions.

Architecture: Rule engine, knowledge base and traceable decisions.

Challenge: Incomplete knowledge, conflicting rules and maintenance drift.

Review gate: Review rule coverage, conflict handling and explanations with domain experts.

Incomplete knowledge, conflicting rules and maintenance drift.

Supervised prediction

Milestones: Define labels → split data → train → calibrate → evaluate.

Architecture: Versioned features, training pipeline and inference service.

Challenge: Label quality, leakage, imbalance and distribution shift.

Review gate: Evaluate held-out performance, relevant subgroup errors and abstention.

Label quality, leakage, imbalance and distribution shift.

Clustering & anomaly detection

Milestones: Define normality → choose distance → inspect clusters → validate alerts.

Architecture: Feature pipeline, statistical or learned baseline and review queue.

Challenge: No definitive labels; unstable clusters, false alarms and changing baselines.

Review gate: Test stability and usefulness with reviewers; do not equate unusual with harmful.

No definitive labels; unstable clusters, false alarms and changing baselines.

Generative language models

Milestones: Evaluate model → constrain context → test outputs → monitor use.

Architecture: Model endpoint or local inference, prompt templates and output controls.

Challenge: Unsupported claims, injection, privacy, misuse and evaluation ambiguity.

Review gate: Assess factual support, harmful outputs, abstention and human-review routes.

Unsupported claims, injection, privacy, misuse and evaluation ambiguity.

Retrieval-augmented generation

Milestones: Authorise sources → index → retrieve → generate → verify citations.

Architecture: Permission-aware retrieval, model inference and citation provenance.

Challenge: Stale sources, retrieval misses, cross-user leakage and unsupported citations.

Review gate: Test retrieval and generation separately, including access-denied and no-answer cases.

Stale sources, retrieval misses, cross-user leakage and unsupported citations.

Computer vision

Milestones: Collect representative images → annotate → train → validate conditions.

Architecture: Image decoding, preprocessing, model inference and output interpretation.

Challenge: Lighting, occlusion, demographic coverage, image privacy and compute costs.

Review gate: Test representative environments and shift; include uncertain or unsupported images.

Lighting, occlusion, demographic coverage, image privacy and compute costs.

Speech & audio

Milestones: Capture audio → segment → transcribe/classify → validate speakers.

Architecture: Audio pipeline, speech model and timing or transcript outputs.

Challenge: Accent variation, noise, diarisation errors, consent and latency.

Review gate: Evaluate task-appropriate errors across speaking conditions and user groups.

Accent variation, noise, diarisation errors, consent and latency.

Recommenders & ranking

Milestones: Define objective → test relevance → pilot exposure → monitor feedback.

Architecture: Candidate retrieval, ranking model, experimentation and feedback logs.

Challenge: Feedback loops, exposure inequality, popularity bias and objective gaming.

Review gate: Balance relevance with user welfare and exposure; review online and offline evidence.

Feedback loops, exposure inequality, popularity bias and objective gaming.

Forecasting & time series

Milestones: Order data → backtest → model seasonality → quantify uncertainty.

Architecture: Time-aware feature pipeline, rolling evaluation and forecast monitoring.

Challenge: Temporal leakage, regime change and overconfident long-range predictions.

Review gate: Use time-based validation and uncertainty checks; compare simple baselines.

Temporal leakage, regime change and overconfident long-range predictions.

Reinforcement learning

Milestones: Define rewards → simulate → constrain actions → evaluate policy.

Architecture: Environment, agent policy, reward signals and action boundary.

Challenge: Reward gaming, unsafe exploration and simulator-to-world mismatch.

Review gate: Test constrained policies in safe environments before consequential real-world actions.

Reward gaming, unsafe exploration and simulator-to-world mismatch.

Agents & autonomous tools

Milestones: Scope tools → enforce permissions → test plans → supervise actions.

Architecture: Planner, tool gateway, bounded memory, audit trail and approval controls.

Challenge: Excessive permissions, indirect injection, cascading errors and irreversible actions.

Review gate: Verify least privilege, stop conditions, action review and recovery under failure.

Excessive permissions, indirect injection, cascading errors and irreversible actions.

Edge & embedded AI

Milestones: Profile hardware → optimise → test device → update safely.

Architecture: On-device inference, constrained memory/power and signed update path.

Challenge: Latency, thermal limits, offline operation and physical safety constraints.

Review gate: Measure on target hardware and validate fallback, updates and failure behaviour.

Latency, thermal limits, offline operation and physical safety constraints.

Federated & privacy-preserving AI

Milestones: Agree participation → distribute updates → aggregate → evaluate leakage.

Architecture: Participant clients, aggregation coordinator and privacy controls.

Challenge: Non-identical data, poisoned updates, privacy leakage and participant dropout.

Review gate: Test aggregation resilience and privacy assumptions; decentralisation alone is not privacy.

Non-identical data, poisoned updates, privacy leakage and participant dropout.

Scientific & causal modelling

Milestones: Specify assumptions → calibrate → validate → assess sensitivity.

Architecture: Model equations or learned components, provenance and reproducible analysis.

Challenge: Confounding, identifiability, uncertain parameters and invalid extrapolation.

Review gate: Check assumptions and independent evidence; predictive fit alone does not establish causality.

Confounding, identifiability, uncertain parameters and invalid extrapolation.

Multimodal & hybrid systems

Milestones: Align modalities → integrate components → test interfaces → evaluate system.

Architecture: Combined text, image, audio, rules or retrieval components.

Challenge: Cross-modal errors, missing inputs, inconsistent meanings and complex dependencies.

Review gate: Test each component and interactions, including conflicting or unavailable modalities.

Cross-modal errors, missing inputs, inconsistent meanings and complex dependencies.

Purpose & proportionality

Governance & applicability

Communication & research claims

Separate measured results, assumptions and hypotheses. Report methods, limitations, exclusions and uncertainty. Protect private material while preserving reproducibility and source attribution.

Closure & residual obligations

Specify ownership after handover, record retention, deletion, appeal support and incident follow-up. End active inference deliberately; archive authorised evidence and verify that credentials, integrations and resources are retired.

Specify ownership after handover, record retention, deletion, appeal support and incident follow-up. End active inference deliberately; archive authorised evidence and verify that credentials, integrations and resources are retired.

Finish responsibly

  1. Complete acceptance review

    Reconcile objectives against evidence, document residual risks and record the decision: accept, restrict, rework or stop. Include independent review where the stakes require it.

    Evidence: acceptance record, unmet requirements, limitations and accountable decision owner.

  2. Transfer operational ownership

    Hand over versioned artifacts, runbooks, monitoring, support routes, permissions and training. Identify responsibilities for incidents, changes and ongoing stakeholder concerns.

    Evidence: handover record, responsible owners and verified access/support arrangements.

  3. Retire or replace

    Plan withdrawal, notify relevant users, stop inference and scheduled jobs, revoke unnecessary credentials and retire resources. Validate replacement behaviour and maintain appropriate routes for unresolved decisions.

    Evidence: retirement checklist, resource checks, migration tests and communication record.

  4. Retain authorised evidence

    Keep only records justified by research, contractual or applicable retention requirements. Apply agreed deletion to unnecessary data and document limitations of what can be reproduced after deletion.

    Evidence: archive index, retention decisions and deletion verification.

  5. Close and learn

    Record lessons, unresolved research questions, benefits and harms. Close outstanding actions or assign continuing owners. Feed findings into future work without losing source provenance.

    Evidence: final report, lessons register and owned follow-up actions.

Use the appropriate evidence: a research prototype, public recommender, clinical model and autonomous device require different acceptance criteria. A shared lifecycle provides structure; task-specific validation determines whether a particular claim is justified.

DISTINCT QA REALM · VERIFY BEFORE EXPANDING

Quality assurance & validation

Use this review after the project and testing sections. QA also belongs throughout development: this is a focused check that the page works, communicates accurately and fulfils its learning purpose.

What to do next

Complete one journey first, then broaden coverage. Scroll through the steps and expand only the detail you need.

1. Run a baseline

Open one project, keep its example inputs and run it. Record the project, inputs and expected result; inspect the actual output.

Check for: A valid output and a clearly stated baseline expectation.

2. Save baseline evidence

In Record, Compare & Explain, label the run Baseline, add your expectation and observation, then save the latest run.

Check for: A saved baseline with inputs, output and context.

3. Change one input

Return to the same project and change one parameter or one data element. Predict the effect before running again; label and save the changed run.

Check for: A comparison in which the changed variable is identifiable.

4. Compare the results

Select the two saved runs of the same project. Inspect changed inputs and outputs; explain an unexpected difference or an unchanged result.

Check for: A reasoned observation, with uncertainties recorded.

5. Break and repair

Run the verification suite without a fault. Inject each controlled fault, inspect the failures, then select Apply fix & rerun. These fixes remove simulated harness faults rather than patching the source.

Check for: A recorded baseline, detected failure and successful regression rerun.

6. Check downloads

Export experiment records, verification evidence and the research report. Open each downloaded file and check that it contains the intended run, outputs and notes.

Check for: Readable exports containing the expected evidence.

7. Review project plans

Open each Gantt tab, change the timeline scale, inspect review gates and the schedule table, then download and open a chart.

Check for: Consistent chart/table timing and a usable SVG download.

8. Record QA findings

In the QA realm, enter device/browser, set each reviewed check’s status and add expected-versus-actual evidence. Leave unreviewed checks as Not tested.

Check for: A truthful checklist with open issues and a provisional acceptance decision.

9. Repeat across projects

Repeat the project journey for all ten experiments, including invalid inputs and abstention cases. Check file handling for the document and image projects.

Check for: Coverage across every project, including error paths.

10. Review access and layout

Test phone and desktop layouts, keyboard controls, focus, zoom, labels, horizontal scrolling and reduced-motion behaviour. Check that text stays readable and controls remain reachable.

Check for: Device-specific findings and accessible routes through the page.

11. Fix and recheck

Prioritise failures by impact. Record an owner and corrective action; reproduce the issue, fix it, then rerun the affected journey and regression checks.

Check for: A documented fix with retest evidence and remaining limitations.

12. Decide the next build

Review whether the page meets its learning purpose. Once material defects are resolved, evaluate one trained model against a baseline on held-out examples.

Check for: A justified acceptance decision and a bounded next-stage plan.
