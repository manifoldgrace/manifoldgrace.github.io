# Client portal activation

GitHub Pages serves `/ai-agency/portal.html`. Supabase provides the hosted Auth API and PostgreSQL Data API. The existing media Worker is separate and its owner upload key does not grant client access.

## Current state

Portal UI, sample journey, Auth integration and migration are implemented. No Supabase project is connected; real registration stays disabled until activation. Preview is tab-memory only and does not simulate a secure login. No password, business record or preview content is written by this application to localStorage. Supabase sessions use sessionStorage (cleared when the tab closes).

## Activate

1. Create or select an owner-controlled Supabase project. Choose an appropriate region after reviewing its hosting/data-processing terms.
2. Apply `001-client-workspaces.sql` in its SQL editor. It creates private business, task and activity tables. Activity is generated by database triggers; clients cannot edit it.
3. Enable email/password Auth, email confirmation and TOTP MFA. Set minimum password length to 12; configure Auth rate limits. Disable unused sign-in methods. Use production SMTP for verification and recovery emails; configure sender identity and delivery before inviting clients.
4. Set Site URL and allowed redirect URL to `https://manifoldgrace.github.io/ai-agency/portal.html`. The password-recovery flow also returns here.
5. Put ONLY the project URL and publishable (or legacy anon) key in `portal-config.js`. Never use a service-role key. These public values are designed for browser use; security is enforced by database row policies. Config is intentionally empty until a project is available.
6. Verify registration, inbox confirmation, password login, mandatory mobile authenticator enrollment, sign-out, return login and password recovery on the production URL.
7. Create two test accounts: AAL1 sessions must not read or write business/task/activity rows; AAL2 account B must not read or write account A's rows, including guessed business/task IDs and owner changes. Authenticated users must not insert, update or delete activity directly. Run `rls-check.sql` with real test UUIDs to validate the database boundary before activation for other clients.
8. Verify two ventures stay separate and appear after signing in again. Add a backup authenticator and verify it works. Review account/data deletion support, privacy information and backup/retention choices before wider client rollout.

## User journey

Create account with email as username → verify email → sign in → enroll mobile authenticator → add first venture → complete brief → add milestone/tasks → shortlist agent services → switch ventures → sign out. On return: password → authenticator → private dashboards. Gmail is an email address here, not Google OAuth; no Gmail mailbox access is requested. The user enters their own password, which Supabase Auth manages.

On a single phone, copy the manual setup key into an authenticator instead of scanning the QR code. TOTP does not require a native mobile app for this portal or SMS. A second authenticator is supported as a backup. Do not promise recovery codes: Supabase does not provide them for this flow. Lost access to all factors requires a verified account-recovery support process.

## Structure and future execution

- `auth.users`: provider-managed identity, email verification, passwords and MFA factors.
- `agency_businesses`: owner ID, purpose, customers, offer, stage, milestone and service shortlist.
- `agency_tasks`: actions and completion by business ID.
- `agency_activity`: server-generated workspace changes (not a tamper-proof compliance archive).
- RLS requires both ownership and `aal2` on every client data operation. IDs alone confer no access. Owner and task identities cannot be changed.

There is no agent executor in this release. Add a server-side Worker/Edge Function for agent jobs, integrations, secrets, approvals, usage controls and execution logs. Every endpoint must validate the user's JWT, second factor, business ownership and requested permissions before queuing work. Third-party/API secrets belong in server secret storage, never these public files. Keep client uploads in private storage with the same ownership checks; the existing public media gallery is unsuitable for private business documents. SMS MFA would require separate provider configuration and delivery costs.
